# ERC-20 REST Service for RESTgym

This repository is the RESTgym integration of ERC-20 REST Service. It is meant to be used as a Git submodule of [RESTgym](https://github.com/restgym/restgym) (in `apis/erc20/`), which builds its Docker image and runs it with the testing tools: it does not work on its own.

## How RESTgym runs it

The image starts from the base image of RESTgym for Java 17 (`restgym/api-base:java17`), which contains the proxy and the collection of code coverage. Ganache, a local Ethereum blockchain, runs in the container (deterministic accounts, network id 1337); the API connects to it as `nodeEndpoint`, with the first account as `fromAddress`. When the API is ready, `init-contract.py` deploys a test token contract through the API (`POST /deploy`). The proxy rewrites the requests of the tools (`rewrite-contract-address.py`): valid contract addresses invented by the tools are replaced with the address of the test contract, so that the operations on a contract reach an existing one, while invalid addresses and those of the contracts deployed by the tools reach the API unchanged (see [Rewriting of contract addresses](#rewriting-of-contract-addresses)). The tools reach the API through the proxy of RESTgym, on port 9090.

## Changes made by RESTgym

### API

None.

### Specification

The original specification is `original/erc20-swagger.json` (Swagger 2.0): the specification that the API serves at `/v2/api-docs` (springfox 2.7.0), saved unchanged from the API running in its RESTgym container (2026-10). `erc20-openapi.json` and `erc20-openapi.yaml`, given to the tools, have the same content (OpenAPI 3.0.1, in JSON and YAML). Besides the conversion to OpenAPI 3.0.1, they differ from the original in:

- **Request bodies completed.** `ApproveAndCallRequest` declares `spender`, `value` and `extraData` (it has no properties in the original), and `TransferFromRequest` declares `value` (only `from` and `to` in the original). springfox leaves them out because their getters are not public, but the API reads them: the specifications given to the tools describe the requests that the API accepts.
- **Formats added** to `ContractSpecification`: `int32` for `decimalUnits` and `int64` for `initialAmount`.
- **Schemas renamed**: `TransactionResponse«ApprovalEventResponse»` and `TransactionResponse«TransferEventResponse»` (springfox names, with the characters « ») are `TransactionResponseApprovalEventResponse` and `TransactionResponseTransferEventResponse`.

### Integration

- The local blockchain, the test contract and the rewriting of contract addresses described above.

### Rewriting of contract addresses

11 of the 13 operations act on a contract on the blockchain, given by its address in the path (`/{contractAddress}/...`, e.g., `/{contractAddress}/name`, `/{contractAddress}/transfer`). The API has no operation that lists the contracts: a tool knows the address of a contract only if it deploys one (`POST /deploy` answers its address, a string without a name in the specification, hard to link to `contractAddress`). With the addresses that the tools make up, the API would only answer errors. So RESTgym gives them one contract:

1. When the API is ready, before the proxy starts, `init-contract.py` deploys a test token (`POST /deploy`: `TestToken`, symbol `TST`, 1,000,000 units, 18 decimals) and saves its address in `/tmp/erc20_contract_address.txt`.
2. The proxy loads `rewrite-contract-address.py` (`RESTGYM_PROXY_SCRIPTS` in `entrypoint.sh`), which reads that address at the first request, and remembers the addresses of the contracts that the tools deploy (the answers 200 of `POST /deploy`).
3. In every request whose path is `/<address>/<operation>` (with `<operation>` one of `decimals`, `name`, `symbol`, `totalSupply`, `balanceOf`, `allowance`, `approve`, `transfer`, `transferFrom`, `approveAndCall`, `version`, and anything after it, e.g., `/balanceOf/{ownerAddress}`, and any query string, e.g., `/allowance?ownerAddress=...&spenderAddress=...`), the script replaces `<address>` with that of the test contract only if it is a **valid address of an unknown contract**: `0x` followed by 40 hexadecimal digits, other than the address of the test contract and of the contracts deployed by the tools (in any case of the letters). For example, `GET /0x1234567890abcdef1234567890abcdef12345678/name` reaches the API as `GET /0x<test contract>/name`. It logs each rewriting (`[ERC20] Rewriting path: ...`) and each contract deployed by a tool (`[ERC20] Contract deployed by the tool: ...`) in the output of the container (`logs/erc20-stdout.log` in the results of the run).

The script does not change:

- **Invalid addresses** (e.g., `0xdeadbeef`, `string`, or 41 digits): they reach the API, which answers 500 (`Unable to determine sync status of node`), so the tools can find these failures.
- **The addresses of the contracts deployed by the tools**: their operations act on them (e.g., `transfer` changes the balances of the contract of the tool, and `name` answers its name).
- `/config` and `/deploy`, the other parameters (e.g., `ownerAddress`, `spenderAddress`) and the bodies.

Consequences:

- **Valid addresses never reach the API as such, unless they are of known contracts**: the API never answers about a valid address without a contract.
- **`results.db` stores the rewritten path**, not the one sent by the tool: the requests are stored when their responses arrive, after the rewriting.
- **The rewriting does not change the code coverage**: the code of the API that each operation runs does not depend on the contract (the contracts run in Ganache, whose code is not measured). It lets the tools run the 11 operations without knowing an address.
- If the deployment of the test contract fails (or its verification, `GET /{contractAddress}/name`), the container stops before the tool starts (`logs/erc20-stdout.log` then has `ERROR: The deployment of the test contract failed.`): it is a startup failure, and RESTgym runs the run again (up to `max_attempts` times), so that no run is made without the test contract.

## Endpoints that may interfere with authentication

RESTgym handles the authentication of the requests, and the tools are not aware of it: an endpoint that ends or changes the session of RESTgym (e.g., logout, login as another user, change or deletion of the user of the proxy, of its password or of its roles) may make the tools fail for the rest of the run. The proxy blocks the requests that would end its session (`471 Blocked by RESTgym`), instead of removing the endpoints from the specifications given to the tools.

None: RESTgym does not authenticate the requests to this API (it needs no authentication: `rewrite-contract-address.py` only rewrites contract addresses), so no endpoint can end or change a session of RESTgym.
